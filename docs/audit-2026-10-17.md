## 2. Security

### 2.1 Backend (.NET API)

**SEC-01 · High · Discord OAuth links accounts on an unverified email → account takeover.**
`src/FFXIV.Api/Controllers/AuthController.cs:195-207` finds an existing user by the Discord email and links the Discord id to it; `src/FFXIV.Infrastructure/Identity/DiscordOAuthService.cs:88-93` never reads Discord's `verified` field. An attacker creates a Discord account with the victim's email (unverified), signs in with Discord, and is logged into the victim's account. Fix: deserialize `verified`; only link/create when `verified == true`; otherwise require the user to sign in with their password to link.

**SEC-02 · Medium · OAuth `state` is generated but never checked (login CSRF).**
`AuthController.cs:164-171` creates `state`; `DiscordCallback` ignores it and the callback page (`frontend/src/app/auth/discord/callback/page.tsx:22`) reads only `code`. Fix: store `state` client-side (sessionStorage/cookie) before redirect, send it back, and reject mismatches; or adopt PKCE.

**SEC-03 · High · No brute-force protection on `/api/auth/*`.**
No `[EnableRateLimiting]` on login/register/refresh/discord (`AuthController.cs`), and Identity lockout never engages: `CheckPasswordAsync` (`AuthController.cs:87`) does not record failures and `Lockout` options are unset (`src/FFXIV.Infrastructure/DependencyInjection.cs:AddIdentityServices`). Fix: a per-IP sliding-window "auth" policy, `SignInManager.CheckPasswordSignInAsync(user, pw, lockoutOnFailure: true)` or `AccessFailedAsync`, `Lockout.MaxFailedAccessAttempts`/`DefaultLockoutTimeSpan`.

**SEC-04 · High (availability) · The three rate limiters are global, not per client.**
`src/FFXIV.Api/Program.cs:57-90` uses `AddFixedWindowLimiter` with no partition key, so the limits are shared by every caller: 5 feedback submissions per hour for the whole site, 20 solver calls/min, 60 analytics events/min. One crawler or one abusive client locks out everyone, and solver polling (`GET solve/{jobId}`) shares the same 20/min bucket as submissions. Fix: `AddPolicy("…", ctx => RateLimitPartition.GetFixedWindowLimiter(userId ?? clientIp, …))` and add `app.UseForwardedHeaders(...)` (with `KnownNetworks`/`KnownProxies` cleared for Container Apps) so `RemoteIpAddress` is the client, not the ingress. Today no `ForwardedHeaders` configuration exists anywhere, so `CraftingController.cs:196` (`clientId = userId ?? RemoteIpAddress`) also makes every anonymous solver user share one 5-job allowance.

**SEC-05 · High · Unauthenticated CPU/memory DoS via `linesPerMacro`.**
`src/FFXIV.Domain/CraftingEngine/MacroExporter.cs:33-47` loops `for (i = 0; i < lines.Count; i += options.LinesPerMacro)`; `src/FFXIV.Application/Crafting/CraftingMapper.cs:237` copies the client value unvalidated; `POST /api/crafting/export-macro` has no auth and no limiter. `linesPerMacro: 0` → `DivideByZeroException` (500); `linesPerMacro: -1` → infinite loop appending strings until the 0.5 GiB replica is OOM-killed. Fix: validate `1 ≤ LinesPerMacro ≤ 15` in the handler and clamp in `MacroExporter`.

**SEC-06 · High · Anonymous `/sufficiency` runs the solver inline, outside the job queue and limiter.**
`src/FFXIV.Api/Controllers/RecipesController.cs:221-242` (no `[Authorize]`, no limiter) → `src/FFXIV.Application/Journey/StatSufficiencyService.cs:91-99` runs a greedy solve with `TimeBudgetMs = 3000` on the request thread; the cache key is the exact stat tuple, so `craftsmanship=1,2,3…` each miss. Fix: per-IP limiter, bucket stats in the cache key, lower the budget, or route through `ISolverJobService`.

**SEC-07 · High · Unbounded in-memory cache with attacker-chosen keys.**
`DependencyInjection.cs:85` `AddMemoryCache()` has no `SizeLimit`; `src/FFXIV.Infrastructure/Caching/InMemoryCacheService.cs:9,33` keeps a `HashSet<string> _keys` that is never pruned on eviction. Unauthenticated key spaces: `gearset:{job}:{level}:{profile}` where `profile` is free text (`GetGearRecommendationsQueryHandler.cs:27`; `StatWeightProfiles.GetProfile` accepts anything, 24 h TTL), `lodestone:preview:{name}:{server}` (1 h), `materialtree:{recipeId}:{quantity}` (999 × every recipe, 24 h), search hashes of unbounded `q`/`page`. Fix: `SizeLimit` + `Size` per entry, eviction callbacks (or a change token per prefix) instead of `_keys`, whitelist `profile`, cache trees per recipe and scale at read time, cap `name`/`q` length.

**SEC-08 · High (privacy) · Public rotation list exposes author emails.**
`src/FFXIV.Infrastructure/Persistence/Repositories/SharedRotationRepository.cs:134,148` project `u.DisplayName ?? u.UserName`, and `UserName` is the email (`AuthController.cs:55-57`, `:214`); `GET /api/rotations` and `GET /api/rotations/{id}` are anonymous and return `AuthorName`. Every author who skipped the optional display name is listed by email. Fix: `DisplayName ?? "Anonymous"` (or a generated handle); stop using the email as `UserName`.

**SEC-09 · Medium · Lodestone endpoints: outbound amplifier, id squatting, user-controlled URL path.**
`GET /api/profile/lodestone-preview` is anonymous and unlimited (`ProfileController.cs:314-333`) and performs up to three HTML scrapes of finalfantasyxiv.com per unique name (`LodestoneService.cs:29,76,104`) — the API's egress IP can get banned for everyone. `UpdateProfileCommandHandler.cs:34-35` lets any user set an arbitrary `LodestoneId`, which is unique (`CharacterProfileConfiguration.cs:34-36`): claim a victim's id and their import fails with a 500 forever. NetStone interpolates the id into the URL path, so `"../../x"` steers the fetched Lodestone URL (host fixed). Fix: `^\d{1,20}$` validation, make the id import-only, map unique violations to 409, per-IP limiter and negative caching on preview.

**SEC-10 · Medium · Solver jobs readable/cancellable by anyone holding the id; unbounded queue wait; raw exception text to clients.**
`SolverJobService.cs:55,78` never compare `ClientId`; ids are 48-bit. `:103` `WaitAsync` has no timeout and the hard timeout is armed only after a permit (1 permit on a 0.25 vCPU box). `:242` `SetFailed(job, ex.Message)`. With `minReplicas: 0` all jobs/results vanish on scale-down (202 then 404). Fix: owner check, `CancelAfter` before `WaitAsync`, generic failure messages, a separate polling limiter.

**SEC-11 · Medium · `/health` is a public probe that hits SQL and XIVAPI and returns exception messages.**
`Program.cs:188-192` + `src/FFXIV.Api/Health/HealthCheckResponseWriter.cs:47` (`error = e.Value.Exception?.Message`, plus `lastDataSync`). Each anonymous hit wakes the auto-paused serverless database and spends an XIVAPI call. Fix: keep `/health/live` public for the platform; protect `/health` (admin key or internal), strip exception text in production, rate limit it.

**SEC-12 · Medium · Refresh tokens stored in plaintext, 30-day lifetime, never pruned, no reuse detection.**
`src/FFXIV.Infrastructure/Identity/TokenService.cs:56-61,70-88`. Fix: store SHA-256 hashes and look up by hash; revoke the token family on reuse of a revoked token; add a cleanup job.

**SEC-13 · Medium · Request fields not bounded against DB max lengths → `SqlException` 500s.**
Profile (`CharacterName` 128, `ServerName` 64, `AvatarUrl` 512 — not even checked to be http(s)), rotations `Algorithm` 64, favourites `Note` 1024, feedback `PageUrl` 2048, analytics `Metadata`/`PageUrl`/`Referrer`; `AnalyticsEvents` has no retention job and may store OAuth `code`s from callback URLs. Saved lists: quantities only checked `< 1` (`SavedListsController.cs:218,301,337`) → `int` overflow to negative quantities in `RecipeTreeResolver.cs:184,224`; list JSON grows without bound (O(n²) re-serialisation per add). Fix: `[MaxLength]`/explicit checks mirroring the EF configurations, quantity ≤ 999, items-per-list cap.

**SEC-14 · Low · Market/cost endpoints are an anonymous Universalis proxy; upstream errors surface as 500s.**
`MarketController.cs:31-56` (100 ids/request, no limiter), `RecipesController.cs:179-209`, `CraftPlansController.cs:287-307`. `UniversalisClient.cs:74 EnsureSuccessStatusCode()` and the resilience pipeline's `RateLimiterRejectedException` are uncaught; `CostEstimationService.cs:227` puts `ex.Message` into user-visible warnings; cache key uses raw-case `world`. Fix: per-IP limiter, map to 503 with a generic message, normalise casing.

**SEC-15 · Low · Paging/LIKE inputs unbounded.** `page` only checked `< 1` → `(Page-1)*PageSize` overflow → negative `OFFSET` 500; `q` unbounded and `%`/`_`/`[` unescaped (parameterised, so no injection, but `q=%%` forces scans); `GearController.cs:203-221` does not validate `job` before `LIKE '%job%'`.

**SEC-16 · Low · Error detail leakage.** `src/FFXIV.Api/Middleware/ExceptionHandlingMiddleware.cs:29-44` echoes `ArgumentException.Message`; `GatheringGuideService.cs:54` throws `ArgumentException` on duplicate item ids (dead `ToDictionary`), surfacing the internal message as a 400.

**SEC-17 · Low · Misc.** `AllowedHosts: "*"`; `UseHttpsRedirection` is a no-op in production without an https port (the ingress redirects anyway); `appsettings.Development.json` (dev SQL password, dev JWT key) is published into the container image by default — placeholders, but exclude it; `Export/appsettings.json` carries the same dev values.

**Clean (backend):** object-level authorization is correct on craft plans, saved lists, favourites, notifications, profile and rotation delete; no raw SQL anywhere; outbound URLs are whitelisted/escaped (Universalis `world`, XIVAPI fields, Garland ids); solver budgets (1–60 s) and `MaxSteps` (1–100) are bounded server-side with cancellation; `RecipeTreeResolver` has a depth cap and cycle detection; read paths use `AsNoTracking`; user-scoped columns are indexed; Swagger is dev-only; `AdminApiKeyFilter` is constant-time and closed by default; CORS is origin-restricted; JWT validation covers issuer/audience/lifetime/key; the container runs as non-root.

### 2.2 Frontend

**SEC-18 · Medium · No security headers.** Live response carries only HSTS (Vercel default). No CSP (not even report-only), `X-Content-Type-Options`, `X-Frame-Options`/`frame-ancestors`, `Referrer-Policy`, `Permissions-Policy`; `x-powered-by: Next.js` is exposed. `frontend/next.config.ts:51-58` already has a `headers()` hook — add them there and `poweredByHeader: false`. Allow-list needed by a CSP: self, `v2.xivapi.com`, `img2.finalfantasyxiv.com`, `cdn.discordapp.com`, the API origin, `*.ingest.us.sentry.io`, `/_vercel/insights`.

**SEC-19 · Medium · Refresh token lives in `localStorage` for 30 days.** `frontend/src/contexts/AuthContext.tsx:46,62,66,112`. Any XSS (first-party or via Sentry/Vercel scripts or a compromised npm package) exfiltrates a long-lived credential. Mitigation: httpOnly `SameSite` cookie issued by the API (CORS already allows credentials) or a Next route handler as BFF; at minimum SEC-18 plus shorter refresh lifetime (rotation already exists).

**SEC-20 · Low · JSON-LD not escaped for `<`.** `src/app/(tabs)/recipes/[id]/page.tsx:63-91` injects `JSON.stringify(...)` without `.replace(/</g, "\\u003c")`; names come from trusted game data today.

**SEC-21 · Low · Unbounded rotation URL parsers.** `src/lib/rotation-codec.ts:36-65`, `src/lib/format-utils.ts:62-69` accept any length/ids and feed WASM (local CPU only). Cap at 100 steps and known action ids.

**SEC-22 · Low · In-flight GET dedup ignores auth.** `src/lib/api-client.ts:57-78` keys on `path` only, so a login/refresh while `GET /api/auth/me` is in flight can hand the new context the old promise. Key on token fingerprint or clear the map in `onUnauthorized`/`handleTokens`.

**SEC-23 · Low · Discord authorisation URL assigned to `window.location.href` unvalidated** (`AuthContext.tsx:140-143`); add an origin check.

**Clean (frontend):** no `postMessage` listeners, no `javascript:` hrefs, no redirect/`returnTo` params, user text in hrefs is `encodeURIComponent`ed, `sendDefaultPii: false`, no token logging, the e2e mock API is not reachable from `src/`, `VERCEL_AUTOMATION_BYPASS_SECRET` is confined to a `server-only` module, `NEXT_PUBLIC_*` surface is only `SITE_URL`, `API_URL`, `SENTRY_DSN`, `DATA_VERSION`, `DATA_BUCKET_SIZE`.

## 3. Reliability and availability

**REL-01 · High · The production API did not answer any HTTPS request during the audit.**
`https://ffxiv-prod-api.thankfulmeadow-2c8d2bc8.eastus.azurecontainerapps.io/health/live` (no DB/XIVAPI dependency) completed the TLS 1.3 handshake but returned no HTTP response within 90 s, 200 s and 60 s attempts; plain HTTP received the ingress 301, so the ingress is up and the replica is not answering. Through the Vercel rewrite, `/api/health` and `/api/recipes/37783` timed out at 20 s. Effect: sign-in, profile, saved lists, rotations library, market prices and Lodestone import were down. Root cause is not visible from here (no Azure access): check `az containerapp revision list`/`logs` for a crash loop or a scale-from-zero that never becomes ready.

**REL-02 · Medium · The deployment design makes cold paths slow by default.** `infra/modules/container-apps.bicep:90-95` `minReplicas: 0`; Azure SQL serverless auto-pauses after 60 min (30–60 s resume); only a liveness probe (`/health/live`, 30 s period, no startup probe) so a slow start can be killed repeatedly; `DependencyInjection.cs:36-37` has no `EnableRetryOnFailure`, so the first requests after a DB pause fail with 500s. Options: add a `startup` probe; `EnableRetryOnFailure()`; a warm ping (scheduled `curl /health/live`) or `minReplicas: 1` (≈ $10–15/month beyond the free grant at 0.25 vCPU / 0.5 GiB).

**REL-03 · Medium · The client turns cold starts into wrong UI states.** `frontend/src/lib/api-client.ts:86-92` aborts every call at 10 s with a plain `AbortError`; `useProfile.ts:41-45` treats that as "cancelled", leaves `profile` null, and `profile/page.tsx:43-45` shows the **create-profile wizard to an existing user**. The same swallow exists in `useFavorites.ts:41-43`, `useItemSearch.ts:128-130`, `useMaterialTree.ts:58-59`, `useGearRecommendations.ts:81-82,120-121`; Lodestone import/refresh/preview routinely exceed 10 s. Fix: abort with `DOMException("…", "TimeoutError")`, surface it as `ApiClientError(408)`, swallow only when the caller's own signal aborted, allow `{ timeoutMs }` per call (60 s for Lodestone), show a "waking up the server" state.

**REL-04 · Medium · `AbortSignal.any` without feature detection.** `api-client.ts:89-91` throws `TypeError` on Safari < 17.4 / Chrome < 116 / Firefox < 124 for every call that passes a signal (profile, favourites, lists, rotations, gear comparison, notifications, craft plans, market, Lodestone) — an installed PWA on iOS 16 loses all signed-in features. Add a 6-line fallback combiner.

**REL-05 · Medium · Manual admin sync can run inline on the HTTP request.** `DataSyncService.cs:183-193`: when the loop's trigger is not armed, `TriggerSyncAsync` awaits the multi-minute sync with the request token; a client disconnect cancels it half-way and `AdminController.cs:46-53` returns 202 even when the run was skipped. Always hand off to the loop.

**REL-06 · Low · Startup smells.** `ConnectionMultiplexer.Connect` synchronously at registration with silent fallback (`DependencyInjection.cs:91-105`); `LodestoneClient.GetClientAsync().GetAwaiter().GetResult()` sync-over-async in a singleton factory (`:289-296`).

## 4. SEO

Live facts: `https://ffxivcrafting.app/robots.txt` → `Sitemap: https://ffxivcrafting.app/sitemap.xml` → **404**; `/sitemap/0.xml` (4 static URLs) and `/sitemap/1.xml` (824 KB, recipe URLs) exist. Home HTML has no canonical and no `og:image`. The same site is served with 200 on `https://ffxiv-crafting-companion.vercel.app`. Real 404s are returned for unknown recipes and paths.

**SEO-01 · High · robots.txt points at a sitemap that does not exist.** `frontend/src/app/robots.ts:13` emits `/sitemap.xml`, but `src/app/sitemap.ts` uses `generateSitemaps`, which produces `/sitemap/[id].xml` only — Next does not generate an index. The ~13.9k recipe URLs are undiscoverable through the sitemap. Fix: list each chunk in `robots.ts` (`sitemap: [\`${BASE}/sitemap/0.xml\`, …]`, computed from `listRecipeIdsServer`) or add `app/sitemap.xml/route.ts` that emits a `<sitemapindex>`.

**SEO-02 · High · No canonical URLs; two hosts serve the site.** Neither `layout.tsx` nor `recipes/[id]/page.tsx` sets `alternates.canonical`; the apex and `.vercel.app` hosts both return 200; the recipe page rewrites query params (`RecipeDetailClient.tsx:84 router.replace`). Fix: `alternates: { canonical: "/" }` in root metadata and `canonical: \`/recipes/${id}\`` in `generateMetadata`; enable Vercel's redirect of the `.vercel.app` domain to the production domain (or a host redirect in `next.config.ts`).

**SEO-03 · High · The only server-rendered content page ships a spinner.** `src/app/(tabs)/recipes/[id]/page.tsx:53-97` fetches the recipe for metadata and JSON-LD, then renders `<RecipeDetailClient />` with no props; the client starts with `isLoading = true` (`RecipeDetailClient.tsx:61,93,121`) and re-fetches the same bucket. Crawlers get JSON-LD plus a spinner: no `<h1>`, no ingredients, no internal links. Fix: pass the recipe (and the expanded material tree) as props and render header, stats, ingredients and the Journey/Simulate links on the server; keep tabs/favourite/quantity client-side.

**SEO-04 · High · Every client page shares the root title and description.** Only `layout.tsx`, `offline/page.tsx` and `recipes/[id]/page.tsx` export metadata. `/recipes`, `/recipes/plan`, `/items/[id]`, `/gear`, `/simulator`, `/simulator/library(/[id])`, `/profile(/lists/[id])`, `/auth/*` are `"use client"` pages titled "FFXIV Crafting Companion — Recipe Explorer, Simulator & Solver". Fix: per-segment server `layout.tsx` files exporting `metadata` (and `robots: { index: false }` for `profile`/`auth`), or server `page.tsx` wrappers around the client components.

**SEO-05 · Medium · Item, journey and library pages are soft-404s, un-indexed and un-sitemapped.** `items/[id]/page.tsx:87-96`, `recipes/[id]/journey/page.tsx:55-62`, `simulator/library/[id]/page.tsx:171-197` render "not found" with HTTP 200 and start as spinners (the library page's SSR `<h1>` reads "Loading..."). ## 9. Rust engine and WASM boundary

Confirmed by a throwaway probe crate against the release profile (the shipped artifact), not by editing the repo.

**RS-01 · High · One trap poisons the solver until reload.** `frontend/src/workers/solver.worker.ts:52,119-122` keeps one `SolverSession` for the worker's life; `:202-204` catches any error and posts `{type:"error"}`; `solver-client.ts:96-99` maps it to a 400 and never recreates the worker (`onerror` only fires for uncaught exceptions). With `panic = "abort"` a Rust panic is a `WebAssembly.RuntimeError` that skips destructors, so the `&mut self` borrow flag stays set and every later call fails with "recursive use of an object detected". Fix: treat `RuntimeError` (or any throw from a session method) as fatal — free the session, reset `wasm-engine.ts`'s singleton promise and re-init, or post `{type:"fatal"}` so the client terminates and recreates the worker; report as 500 to Sentry.

**RS-02 · High · CP (or any state value) above `i16::MAX` traps `begin`.** `crates/xiv-craft/src/solver/mcts/packed.rs:17-34` packs `cp: i16`, `durability: i16`, `progress/quality: u16` and `narrow()` panics instead of saturating; the frontend only rejects `cp <= 0` (`solver-client.ts:203-205`, `StatsInput.tsx:59-60`) and `simulator/page.tsx:148,166` feeds `Number(cpParam)` from the URL straight in. `?cp=40000&solve=true` or a typo bricks the solver (RS-01). Fix: fallible packing (`try_pack` → failed `SolverResult`) or widen to `u16`; validate stats at the boundary with the C# API's bounds.

**RS-03 · Medium · No panic hook.** The panic message (`"cp = 40000 does not fit the packed state"`) is formatted and discarded; JS sees only `unreachable`. Install `console_error_panic_hook` in a `#[wasm_bindgen(start)]` fn (the instance must still be discarded per RS-01).

**RS-04 · Medium · The committed `.wasm` embeds local Windows paths and a username.** `frontend/src/wasm/xiv_craft_bg.wasm` contains `D:\personal\FFXIVCraftingCompanion\crates\…` and `C:\Users\adame\.cargo\registry\…` (panic `Location` strings) — a public asset leaking a username, and bytes that depend on the checkout path so two developers can never produce identical artifacts. Fix: in `scripts/wasm-build.mjs` set `RUSTFLAGS="--remap-path-prefix=<repo>=. --remap-path-prefix=<cargo home>=/cargo"` (or `trim-paths` once stable).

**RS-05 · Medium · Other trapping inputs.** Unclamped `starting_quality` in `greedy_solve`/`begin` (`crates/xiv-craft-wasm/src/engine.rs:163-176,202-222`) and negative `hqQuantity` producing negative starting quality (`crates/xiv-craft/src/hq.rs:35-47`); session call-order misuse uses `expect` (`mcts/mod.rs:218,286,315`) although the exports already return `Result<_, JsError>`; recipe `progressDivider`/`qualityDivider` of 0 divide by zero (`formula.rs:11,25`) — reject `<= 0` in the DTO conversion with `FailReason::RecipeLevelUnavailable`.

**RS-06 · Low · Performance.** `Date.now()` is called through the JS boundary once per MCTS iteration (`mcts/mod.rs:230-233`; up to ~1M calls/s, and wall-clock is non-monotonic) — sample every 64 iterations or pass the remaining budget in; the rollout policy recomputes `exp()` for ≤ 36 candidates per step (`:518-545`) — cache per discrete score; `snapshot()` replays the best sequence every slice.

**RS-07 · Low · Build/toolchain.** No `rust-toolchain.toml`/`rust-version` (artifact built with 1.98.1, CI floats on `stable`); two separate Cargo projects instead of one workspace (two lockfiles, `xiv-craft` compiled twice in CI); no `[lints]` (`unsafe_code = "forbid"`, clippy `all = "warn"`) and clippy/fmt not in CI; `wasm:check` proves provenance (tree hash) not content — with RS-04 fixed a CI rebuild-and-`cmp` becomes possible; generated `xiv_craft.d.ts` types every DTO as `any`; browser searches always use `DEFAULT_SEED`, so "solve again" walks the same tree; the parity replay is one `#[test]` over 3,420 cases so the first mismatch hides the rest.

**RS-08 · Medium · No tests for the wasm-bindgen layer or the worker protocol** (`crates/xiv-craft-wasm/tests/engine.rs` tests only `engine`/`dto` on the host; nothing in vitest touches `wasm-engine.ts`/`solver-client.ts`/`solver.worker.ts`; the single Playwright happy path is the only coverage).
