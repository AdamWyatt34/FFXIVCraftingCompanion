# FFXIV Crafting Companion

Crafting, gathering, gear, and market companion for FFXIV players, with a rotation simulator and solver. Charter (intent, no-go zones, gates, scoping): `.aios/charter.json`.

## Stack and layout

- Backend: .NET 10, Clean Architecture. `src/FFXIV.Domain` (crafting engine, formulas, entities; zero dependencies) -> `src/FFXIV.Application` (MediatR 14 handlers, DTOs) -> `src/FFXIV.Infrastructure` (EF Core SQL Server, Identity + JWT, caching, XIVAPI/Universalis/Lodestone clients, Greedy + MCTS solvers) -> `src/FFXIV.Api` (controllers, Swagger, Serilog, Sentry).
- Static game data: `src/FFXIV.Export` syncs XIVAPI into a SQL Server and writes the JSON the frontend serves (recipes and items in 100-id buckets, per-job gear, a search index, `manifest.json`) by calling the same MediatR handlers as the API. `.github/workflows/data-export.yml` runs it weekly against a service container, force-pushes the output to the orphan `data` branch, and pins the commit in `frontend/data.lock.json` on `main`. The export shapes are the API DTOs; never hand-write them. `tests/FFXIV.Tests/StaticData/TestData/fixture.json` is a frozen slice the exporter wrote (`--fixture-recipes`); the goldens next to it are generated by `StaticDataGoldenTests` and are the reference for every computation ported to the frontend.
- Frontend: Next.js 16 App Router + React 19 PWA in `frontend/` (Tailwind 4, Recharts, Serwist). Node 22. Game data is read from the export, not the API: `scripts/data-fetch.mjs` (the `prebuild` step) places the data set under `public/data/v/<version>/` from `data.lock.json` (codeload tarball of the `data` branch) or from a local export in `FFXIV_DATA_DIR`; without either the build has no recipe pages and no search. `src/lib/static-data/` holds the client, the search port and the DTO rebuilds; `api-client.ts` keeps the API signatures and answers game-data calls from it. Item and gear search run in `src/workers/search.worker.ts` over `search/compact.json` (the index as interned columns; `search/items.json` is the fallback for older data sets), so the 50k-entry index is never parsed on the main thread. `/recipes/[slug]` (`{id}-{item-name}`; a bare id answers a 308 to the slug) renders on demand and is cached per deployment (`revalidate = false`). Unit tests are vitest (`npm test`) and replay the C# goldens in `tests/FFXIV.Tests/StaticData/TestData/goldens/`; `e2e/fixtures/data` is a two-recipe export for Playwright (regenerate with `FFXIV.Export --recipes 37783,35423`).
- Rust: `crates/xiv-craft`, a dependency-free port of the crafting engine and of the greedy and MCTS solvers (`solver` module) that builds for the host and `wasm32-unknown-unknown`. `cargo run --release --example bench` runs the solver benchmarks against the C# numbers. Parity with the C# engine is proven by the JSONL goldens in `tests/FFXIV.Tests/CraftingEngine/TestData/parity/`, written by `ParityGoldenTests` and replayed by the crate's tests. The C# engine is the reference; port changes, never invent them.
- WASM: `crates/xiv-craft-wasm` wraps the crate with wasm-bindgen using the API's DTO shapes. Its output is **committed** at `frontend/src/wasm/` (neither Vercel nor frontend CI has Rust); `npm run wasm:build` in `frontend/` regenerates it and records the `crates/` git tree hash in `BUILD.json`, and `npm run wasm:check` plus the `WasmArtifactTests` xUnit test fail when the artifact is stale. The frontend runs the simulator, the solver and the signed-in stat check from it; there is no API engine mode. Recipe parameters come from the static game data (`craftingParameters` in the recipe export).
- Deploy: Azure Container Apps + Azure SQL via `infra/` Bicep; frontend on Vercel. See `DEPLOYMENT.md`. End-to-end manual test flows: `TESTING_GUIDE.md`.

## Commands

Build/test/run recipe: `.claude/skills/run/SKILL.md`. Short form:

```powershell
dotnet build FFXIVCraftingCompanion.slnx --configuration Release
dotnet test FFXIVCraftingCompanion.slnx --configuration Release
cd frontend && npm ci && npm run lint && npx tsc --noEmit && npm test && npm run build
cd crates/xiv-craft && cargo test && cargo build --target wasm32-unknown-unknown --release
cd crates/xiv-craft-wasm && cargo test
cd frontend && npm run wasm:build && npm run wasm:check   # after any change under crates/; commit src/wasm/
```

Regenerating the parity goldens after an intended C# engine change (the generator test otherwise fails on the first differing byte); `StaticDataGoldenTests` uses the same variable for the static-data goldens:

```powershell
$env:FFXIV_PARITY_GENERATE = "1"; dotnet test FFXIVCraftingCompanion.slnx --configuration Release --filter "FullyQualifiedName~Parity|FullyQualifiedName~StaticDataGolden"; Remove-Item Env:FFXIV_PARITY_GENERATE
```

Exporting the static game data locally (needs the docker SQL Server; `--skip-sync` reuses an already synced database):

```powershell
dotnet run --project src/FFXIV.Export --configuration Release -- --out ./out --skip-sync
```

## Conventions that differ from global defaults

- This repo uses **MediatR**, not the custom Result-aware mediator. Keep new handlers on MediatR.
- Tests use **xUnit + FluentAssertions + NSubstitute**, not Shouldly/Bogus.
- The crafting engine stays in `FFXIV.Domain/CraftingEngine`. Solver implementations stay in `FFXIV.Infrastructure/Solver` behind `IRotationSolver`. Do not move engine rules into Application or Infrastructure.
- Crafting action ids (`ICraftingAction.Id`) are persisted in saved rotations and macros. Never renumber them; any port must reuse the same ids.
- `Recipe.RecipeLevel` is the recipe level (rlvl), not the class job level. Formulas depend on the distinction (see commit bb6e8ad).

## Do not touch without a human

- `src/FFXIV.Infrastructure/Migrations/` (EF migrations)
- `infra/` and `.github/workflows/` (prod deploy and CI)
- `src/FFXIV.Api/appsettings.Production.json`
- `tests/FFXIV.Tests/CraftingEngine/TestData/solver-benchmarks.json` (hand-maintained solver benchmarks)
- `tests/FFXIV.Tests/CraftingEngine/TestData/parity/` (generator-only output of `ParityGoldenTests`; never hand-edit, regenerate only for an intended engine change)
- `tests/FFXIV.Tests/StaticData/TestData/` (`fixture.json` is written by the exporter; `goldens/` by `StaticDataGoldenTests`; never hand-edit either)
- The `data` branch (written only by the Data Export workflow)

## Gotchas

- Solver benchmark fixtures load from `AppContext.BaseDirectory/CraftingEngine/TestData/`, so new fixture files need `CopyToOutputDirectory` in `tests/FFXIV.Tests/FFXIV.Tests.csproj`.
- Local dev needs Docker for SQL Server + Redis (`docker compose up -d`); production uses in-memory caching, no Redis.
- First local run needs a data sync (`POST /api/admin/sync`) to populate items and recipes; it takes minutes.
- The root `package.json` (single dependency `claude`) and root `node_modules` are unrelated to the app. Do not add app dependencies there.
- Backend CI runs only when `src/**`, `tests/**`, or `*.slnx` change; frontend CI only on `frontend/**`.
- `/api/admin/*` needs the `X-Admin-Key` header matching `Admin:ApiKey`; with no key configured the endpoints answer 401.
