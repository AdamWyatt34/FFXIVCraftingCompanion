# FFXIV Crafting Companion

Crafting, gathering, gear, and market companion for FFXIV players, with a rotation simulator and solver. Charter (intent, no-go zones, gates, scoping): `.aios/charter.json`.

## Stack and layout

- Backend: .NET 10, Clean Architecture. `src/FFXIV.Domain` (entities and data shapes; zero dependencies) -> `src/FFXIV.Application` (MediatR 14 handlers, DTOs) -> `src/FFXIV.Infrastructure` (EF Core SQL Server, Identity + JWT, caching, XIVAPI/Universalis/Lodestone clients) -> `src/FFXIV.Api` (controllers, Swagger, Serilog, Sentry).
- Static game data: `src/FFXIV.Export` syncs XIVAPI into a SQL Server and writes the JSON the frontend serves (recipes and items in 100-id buckets, per-job gear, a search index, the crafting meal and medicine catalogue `consumables.json`, `manifest.json`) by calling the same MediatR handlers as the API. An export from a database with no consumable rows fails rather than publish an empty catalogue. When XIVAPI returns an empty, shrunken or unusable consumable snapshot, the sync keeps the stored catalogue, finishes its other passes, then fails without recording the game version, so the next run retries. `.github/workflows/data-export.yml` runs it weekly against a service container, force-pushes the output to the orphan `data` branch, and pins the commit in `frontend/data.lock.json` on `main`. The export shapes are the API DTOs; never hand-write them. `tests/FFXIV.Tests/StaticData/TestData/fixture.json` is a frozen slice the exporter wrote (`--fixture-recipes`); the goldens next to it are generated by `StaticDataGoldenTests` and are the reference for every computation ported to the frontend.
- Frontend: Next.js 16 App Router + React 19 PWA in `frontend/` (Tailwind 4, Recharts, Serwist). Node 22. Game data is read from the export, not the API: `scripts/data-fetch.mjs` (the `prebuild` step) places the data set under `public/data/v/<version>/` from `data.lock.json` (codeload tarball of the `data` branch) or from a local export in `FFXIV_DATA_DIR`; without either the build has no recipe pages and no search. `src/lib/static-data/` holds the client, the search port and the DTO rebuilds; `api-client.ts` keeps the API signatures and answers game-data calls from it. Item and gear search run in `src/workers/search.worker.ts` over `search/compact.json` (the index as interned columns; `search/items.json` is the fallback for older data sets), so the 50k-entry index is never parsed on the main thread. `/recipes/[slug]` (`{id}-{item-name}`; a bare id answers a 308 to the slug) renders on demand and is cached per deployment (`revalidate = false`). Unit tests are vitest (`npm test`) and replay the C# goldens in `tests/FFXIV.Tests/StaticData/TestData/goldens/`; `e2e/fixtures/data` is a two-recipe export for Playwright (regenerate with `FFXIV.Export --recipes 37783,35423`).
- Rust: `crates/xiv-craft` is the dependency-free crafting engine and greedy/MCTS solvers, built for the host and `wasm32-unknown-unknown`. Correctness is pinned by `tests/reference_parity.rs` (Raphael/Teamcraft arithmetic), `tests/goldens/` snapshots regenerated with `XIV_CRAFT_GENERATE=1` only for an intended engine change, and the solver benchmarks (`cargo run --release --example bench`). Teamcraft and Raphael agreeing is ground truth.
- WASM: `crates/xiv-craft-wasm` wraps the crate with wasm-bindgen using the API's DTO shapes. Its output is **committed** at `frontend/src/wasm/` (neither Vercel nor frontend CI has Rust); `npm run wasm:build` in `frontend/` regenerates it and records the `crates/` git tree hash in `BUILD.json`, and `npm run wasm:check` and rust-ci's artifact check fail when the artifact is stale. The frontend runs the simulator, the solver and the signed-in stat check from it; there is no API engine mode. Recipe parameters come from the static game data (`craftingParameters` in the recipe export).
- Deploy: Azure Container Apps + Azure SQL via `infra/` Bicep; frontend on Vercel. See `DEPLOYMENT.md`. End-to-end manual test flows: `TESTING_GUIDE.md`.

## Commands

Build/test/run recipe: `.claude/skills/run/SKILL.md`. Short form:

```powershell
dotnet build FFXIVCraftingCompanion.slnx --configuration Release
dotnet test FFXIVCraftingCompanion.slnx --configuration Release
cd frontend && npm ci && npm run lint && npx tsc --noEmit && npm test && npm run build
cd crates/xiv-craft && cargo test && cargo build --target wasm32-unknown-unknown --release
cd crates/xiv-craft-wasm && cargo test
cd frontend && npm run wasm:build && npm run wasm:check   # after any change under crates/; commit src/wasm/
```

Regenerate the Rust snapshots only for an intended engine change, then replay with the variable unset. Never set `XIV_CRAFT_GENERATE` on CI; it would make snapshot assertions pass vacuously. Every rule change also needs a Raphael/Teamcraft-cited case in `tests/reference_parity.rs`.

```powershell
Push-Location crates/xiv-craft
$env:XIV_CRAFT_GENERATE = "1"
try { cargo test --release } finally { Remove-Item Env:XIV_CRAFT_GENERATE; Pop-Location }
```

`FFXIV_PARITY_GENERATE` is only for the C#-generated static-data goldens:

```powershell
$env:FFXIV_PARITY_GENERATE = "1"
try { dotnet test FFXIVCraftingCompanion.slnx --configuration Release --filter "FullyQualifiedName~StaticDataGolden" } finally { Remove-Item Env:FFXIV_PARITY_GENERATE }
```

Exporting the static game data locally (needs the docker SQL Server; `--skip-sync` reuses an already synced database):

```powershell
dotnet run --project src/FFXIV.Export --configuration Release -- --out ./out --skip-sync
```

## Conventions that differ from global defaults

- This repo uses **MediatR**, not the custom Result-aware mediator. Keep new handlers on MediatR.
- Tests use **xUnit + FluentAssertions + NSubstitute**, not Shouldly/Bogus.
- API integration tests live in `tests/FFXIV.Tests/Api`: `ApiFactory` runs the real pipeline on `WebApplicationFactory` over in-memory SQLite seeded from the static-data fixture, with the Lodestone, Discord and XIVAPI clients substituted. Accounts are created through the API. Give each test its own client (`CreateApiClient`) so the per-address rate limits never couple tests.
- Engine rules and solvers live only in `crates/xiv-craft`. C# keeps `RotationActionCatalog` as an id/name table and never grows engine rules.
- Crafting action ids in `RotationActionCatalog`, the Rust crate and the TS `ACTION_ID_TO_NAME` table must agree; tests compare the catalogs with Rust-generated `tests/goldens/actions.json`. Never renumber persisted ids. They are our ids, not the game's: Precise, Refined and Daring Touch are 100501-100503 because the game's 100443 and 100451 are our Quick Innovation and Trained Perfection. Legacy actions (Focused Synthesis, Focused Touch, Inner Quiet) remain resolvable for saved rotations but are excluded from solver choices.
- `Recipe.RecipeLevel` is the recipe level (rlvl), not the class job level. Formulas depend on the distinction (see commit bb6e8ad).

## Do not touch without a human

- `src/FFXIV.Infrastructure/Migrations/` (EF migrations)
- `infra/` and `.github/workflows/` (prod deploy and CI)
- `src/FFXIV.Api/appsettings.Production.json`
- `crates/xiv-craft/tests/benchmarks/solver-benchmarks.json` (hand-maintained solver benchmarks)
- `crates/xiv-craft/tests/goldens/` (generator-only snapshot output; never hand-edit, regenerate with `XIV_CRAFT_GENERATE=1` only for an intended engine change; `dotnet-random.json` is frozen .NET output and is not regenerated)
- `tests/FFXIV.Tests/StaticData/TestData/` (`fixture.json` is written by the exporter; `goldens/` by `StaticDataGoldenTests`; never hand-edit either)
- The `data` branch (written only by the Data Export workflow)

## Gotchas

- Local dev needs Docker for SQL Server + Redis (`docker compose up -d`); production uses in-memory caching, no Redis.
- First local run needs a data sync (`POST /api/admin/sync`) to populate items and recipes; it takes minutes.
- The root `package.json` (single dependency `claude`) and root `node_modules` are unrelated to the app. Do not add app dependencies there.
- Backend and frontend CI both trigger on `crates/xiv-craft/tests/goldens/actions.json` so the C# and TS action-id checks run on crate-only table changes, as well as on their own source and configuration paths.
- A Vercel deployment does not carry the data set: `scripts/data-fetch.mjs` downloads the locked commit into `frontend/.data/` for the build's server-side reads and points the site at the same commit on jsDelivr (`NEXT_PUBLIC_DATA_BASE`); it falls back to `public/data/v/<version>/` when the CDN cannot serve it (private repository) or for a local export (`FFXIV_DATA_DIR`, which the e2e build uses). Hobby includes 10 GB of Deployment Storage, and the fallback costs about 260 MB per deployment. jsDelivr stores a file only once it has fetched it and refuses fetches from this repository unpredictably (unpacked, the data set is far over its 50 MB package limit), so the build requests every file through it before the deployment goes out and the site reads a file it still refuses from GitHub's raw endpoint for the same commit (`NEXT_PUBLIC_DATA_FALLBACK_BASE`).
- `/api/admin/*` needs the `X-Admin-Key` header matching `Admin:ApiKey`; with no key configured the endpoints answer 401.
